# R1 — Reconstruction probe on frozen RoMaV2 features

New line (R-prefix), started 2026-07-08 after the H-line concluded.

## Goals

- **Project-level:** reduce the information/reconstruction trade-off in
  dense-matching features. Using a matcher like RoMa as a diffusion backbone
  (RAE-style, "Diffusion Transformers with Representation Autoencoders")
  shows a tradeoff between reconstructability and multi-view consistency; we
  want matching features that also retain appearance, so they can serve as a
  generative/RAE-style latent. Endgame (R2+): fine-tune or retrain RoMaV2
  with matching + auxiliary reconstruction loss.
- **R1 (this experiment):** measure the **frozen baseline endpoint** of that
  tradeoff first — how reconstructable are stock RoMaV2 features at each
  pipeline stage, before any fine-tuning? This (a) tests the project premise
  (does the matcher actually discard appearance?), (b) locates *where* in
  the pipeline appearance is lost, and (c) sets the target window R2 must
  close.

## Approach

Freeze RoMaV2 entirely; train small decoders of identical recipe (same
architecture family, data, losses, steps) on cached features from different
pipeline stages; compare reconstruction metrics across stages. The stage
ladder `desc` (matcher input) → `mv` (matcher bottleneck) → `dpt` (head)
localizes the information loss, with `desc` doubling as the
decoder-capacity control: if the same decoder reconstructs well from `desc`
but not from `mv`/`dpt`, the matcher — not the probe — destroyed the
appearance. The `mvdesc` arm then measures what `mv` contributes *beyond*
`desc` (marginal information) and doubles as the architecture candidate for
R2: a backbone skip into the recon decoder would let the matcher keep
specializing in correspondence while the reconstruction gradient shapes the
encoder.

## b3 arm — mid-depth mv_vit tap (launched 2026-07-13)

The mv_vit stage-by-stage PCA visualization
(`experiments/visualizations/r1_visualize_mvvit.py`, outputs `viz_mvvit_{stages,views}.png`)
showed that appearance detail survives through roughly **block 4** of the
matcher ViT: b5–b9 top PCA components turn into smooth positional
gradients (coordinate/match-embedding code dominating), and b10–output
look segment-/noise-like. So the mv collapse is not instantaneous at the
matcher input — it happens in the *second half* of the mv_vit — which
makes the final `mv` tap a pessimistic place to measure (and, for R2, to
attach a recon loss).

The `b3` arm probes this directly: same RAE probe recipe on the **mv_vit
block-3 output tokens for view A** (768ch @ /16, unstacked from the
per-view token layout of the odd/self-attention blocks; the hook asserts
batch 1 because that unstacking is layout-dependent). Cached as `.b3.pt`
sidecars next to the existing pairs; driver `scripts/r1_b3_driver.sh`
(sharded precompute on both GPUs, then training on GPU 0), 3cat split,
results in `results/r1_recon_probe/b3/`.

Expected reading: b3 should land between `desc` (19.56 dB) and `mv`
(12.09 dB). A number near desc would confirm mid-depth taps as the R2
recon-loss attachment point; a number near mv would mean the qualitative
PCA signal overstates what is actually decodable.

**Result (2026-07-13, EMA; `results/r1_recon_probe/b3/metrics.json`):
17.54 dB PSNR / 0.382 SSIM / 0.448 LPIPS** (online within noise). b3
lands ~5.4 dB above `mv` (12.09) and only ~2 dB below `desc` (19.56) —
the quantitative counterpart of the PCA picture: **most of the decodable
appearance is still present three blocks into the matcher** and is
destroyed later, in the second half of the mv_vit. Notably b3 achieves
this with the *smallest* feature of any arm (768ch vs desc's 2048ch).

Qualitatively (`viz_recons.png`, now with a b3 row): b3 reconstructions
keep object identity, texture, and scene layout like desc; the main
degradation is color drift on some objects (e.g. a green toy bus decoded
silver-ish) — hue seems to be among the first things the matcher trades
away. mv/dpt rows remain layout-only prior collapses.

**R2 consequence:** a reconstruction loss attached at a mid-depth mv_vit
tap (~b3/b4) starts only ~2 dB from the descriptor ceiling, so the
training objective has to *preserve* appearance through the later blocks
rather than regenerate it from scratch — a much better-conditioned task
than attaching at the mv output (7.5 dB gap).

## RoMaV2 architecture and probe taps

RoMaV2 is a three-stage dense matcher (`third_party/RoMaV2/src/romav2/`):

1. **Descriptor** (`features.py`, *frozen upstream too*): DINOv3 ViT-L/16
   run per image; intermediate layers 11+17 are the feature stack. This is
   the only pretrained-SSL part — everything below was trained by the
   RoMaV2 authors for matching only.
2. **Matcher** (`matcher.py`, trained): a ViT-B "mv_vit" jointly attends
   over *both* images (alternating self/cross attention, RoPE) — this is
   why all features from here on are pair-conditioned. Its output embeds
   each position for cosine-similarity matching; the softmaxed similarity
   pulls back a Fourier positional-embedding grid of image B to make the
   match embedding. The DPT head (`dpt.py`) fuses the descriptor stack
   (last layer summed with mv + match embedding) into warp + confidence
   at /4.
3. **Refiners** (`refiner.py`, trained): VGG19 fine features + local
   correlation refine the warp from /8 up to full resolution. Not probed —
   they refine an existing warp rather than produce a representation, and
   our extractor stops after the matcher.

Probe taps (`src/romav2_utils.py` hooks, view A, `bidirectional=False`):

```
   img_A                                     img_B

             │                                     │

               ┌────────────────────────────────┐
```

Reading the taps against the pipeline: `desc` sits *before* any
matching-specific computation (pure frozen SSL features of A); `mv` is the
first — and only — bottleneck-shaped representation the matcher produces
(the RAE-comparable point); `dpt` is the last dense feature before the
task readout, and the spot the long-term idea would attach a recon loss
to. Everything below the desc tap is trained with the matching objective
only, which is exactly the regime R1 interrogates.

## Setup

- RoMaV2 vendored in `third_party/RoMaV2` (inference-only upstream; weights
  auto-download to the torch hub cache). Frozen throughout R1.
- Features are pair-conditioned (mv_vit attends over both images). Two
  representations per pair (A, B), extracted via hooks (`src/romav2_utils.py`):
  - `dpt`: fused DPT-head map before `output_conv2`, 128ch @ H/4 — densest,
    ~512x less compressed than an SD-VAE latent, expected easy to decode.
  - `mv`: mv_vit tokens for view A, 1024ch @ H/16 — bottleneck-like, the
    RAE-comparable representation.
  - `desc` (control, added after first results): frozen DINOv3 descriptor of
    A (layers 11+17), 2048ch @ H/16 — the matcher's own input. Same decoder +
    data, so it separates "the matcher discarded appearance" from "our small
    decoder can't decode anything". Cached as `.desc.pt` sidecar files.
  - `mvdesc` (added 2026-07-12): `[desc ‖ mv]` channel concat, 3072ch @ H/16;
    the decoder's input embed doubles as the learned mixing projection.
    Assembled at load time from the cached
    desc+mv — no new precompute. Caveat: since desc alone is near its
    ceiling, the decoder may shortcut to desc and ignore mv — so this arm
    also reports eval-time source ablations (mv channels zeroed / desc
    channels zeroed) in metrics.json. Zeroed inputs are OOD for the decoder,
    so a drop only *upper-bounds* a source's contribution; `mv_zeroed ≈
    full` is still conclusive (mv ignored). It does **not** replace the
    `mv`-only probe, which stays the clean trade-off measurement.
- Data: CO3D `EXTRACTED_CATEGORIES`, standard `split_seqs()` split. Pairs
  alternate near-/far-view conditioning. Features precomputed once (fp16) to
  `/visinf/projects_students/dlcv2025_groupZ/romav2_feats/r1_320/`.
- Decoder (v3, 2026-07-12): `src/decoders.py` RAEDecoder — faithful port of
  the RAE stage-1 decoder (arXiv:2510.11690; `GeneralDecoder` in
  github.com/bytetriper/RAE = HF ViT-MAE decoder): linear embed, trainable
  [CLS] (dropped after decoding), fixed 2D sin-cos pos embeds, pre-LN ViT
  blocks (GELU MLP x4, LN eps 1e-12), final LN + linear 16x16x3 patch head.
  Sizes per paper Table 13; default **ViT-B** (768w/12d/12h, ~87M) — the
  paper's default XL (1152/28) does not fit a 1080 Ti. Probe-forced
  deviations: features finer than /16 are folded to the /16 token grid
  (paper rule p_d=p_e would mean 6400 tokens for dpt @ /4); RAE's encoder
  normalization (paper C.1, final LN with affine cancelled) becomes a
  non-affine LayerNorm on the input tokens, per source slice for mvdesc so
  the zeroed-source ablation stays interpretable. For `mvdesc` the embed
  linear doubles as the mixing projection.
- Recipe (v3 = RAE Table 12 / C.2): L1 + 1.0·LPIPS(VGG, VQGAN-style via
  taming) + 0.75·λ_adaptive·GAN (VQGAN adaptive weight on the last layer,
  vanilla G loss); discriminator = frozen **DINO-S/8** with StyleGAN-T
  spectral-norm conv heads (per-sample "batch" norm as in the released
  code), hinge loss, 8-bit-discretized fakes, DiffAug (translation+color)
  on both sides, inputs resized to 224. Adam lr 2e-4 → 2e-5 cosine, betas
  **(0.5, 0.9) per paper Table 12** (released configs say (0.9, 0.95)), wd
  0, warmup 1/16 of training from zero; LPIPS from step 0, disc updates
  from 6/16, adversarial loss from 8/16 (paper's epoch fractions mapped
  onto 6k steps); EMA 0.9978, **EMA weights are the headline eval**
  (online metrics kept alongside). Noise-augmented decoding (paper 4.3,
  RAE default τ=0.8) is implemented but **off by default** — it exists for
  diffusion-sampling robustness and would blur the reconstructability
  read-out (`--noise-tau`). Hardware deviations: batch 8 (paper 512), 6k
  steps (paper 16 IN1k epochs), fp32 (Pascal), 320px CO3D pairs in [0,1]
  (RoMaV2 convention; losses/disc operate on [-1,1] as upstream).
  **Probe caveat, GAN edition:** v2 dropped the GAN so the decoder couldn't
  hallucinate; v3 restores it for faithfulness to RAE. Read PSNR/L1
  (hallucination-punishing) and LPIPS (hallucination-tolerant) together,
  and compare arms — the frozen features still differ only in what they
  carry, since decoder/recipe are identical across arms.
- Recipe (v1, for the table above): L1 + 0.1 LPIPS(alex), 6k steps Adam
  2e-4 warmup+cosine, no GAN, small ConvDecoder (~5-8M).

## Not used: pretrained RAE decoders

Considered reusing the released RAE decoder checkpoints instead of training
our own. **What they are** (HF `nyu-visionx/RAE-collections`, MIT; code
`github.com/bytetriper/RAE`; paper arXiv:2510.11690):

- ViT-XL decoder bodies under `decoders/dinov2/wReg_{small,base,large}`
  (~12 GB dir; SigLIP2/MAE variants exist alongside), each trained against
  one *frozen DINOv2-with-registers* encoder's final-layer patch tokens.
- Trained on ImageNet-1k at 256px with LPIPS + GAN (discriminator with a
  scheduled loss weight); latents go through a batchnorm-like per-channel
  normalization layer whose running stats ship with the checkpoint — the
  decoder expects *normalized* tokens, e.g. DINOv2-B → latent [768, 16, 16].
- Reconstruction quality: rFID 0.57 (DINOv2-B) — VAE-grade. This is the
  paper's core claim: frozen SSL tokens lose almost nothing decodable.

**Why they don't drop into R1** — three independent mismatches:

1. *Feature space.* Every arm here is out-of-contract: `desc` is DINOv3
   ViT-L **intermediate** layers 11+17 concatenated (2048ch) — different
   model family, different layers, different channel stats than
   DINOv2-wReg final-layer tokens; `mv`/`dpt` are RoMaV2-internal and
   pair-conditioned. A new input projection alone wouldn't fix the
   distribution mismatch — the decoder body would need fine-tuning, which
   defeats the "pretrained" point.
2. *Data/resolution.* They were trained on ImageNet 256px (16x16 token
   grid); R1 evaluates CO3D at 320px (20x20 grid). Pos-embed interpolation
   would run, but cross-domain numbers wouldn't be comparable to our arms
   without retraining on the same data anyway.
3. *Hardware.* Fine-tuning a ViT-XL decoder at 320px does not fit the
   Pascal 1080 Tis (11 GB, no native bf16); R1's ViTDecoder (~27M params,
   ViT-S-scale) is sized for them on purpose. Note it's specifically the
   XL scale that doesn't fit — the transformer *family* does, which is why
   the v2 probe could adopt it.

**What they are still good for:**

- *Calibration of the desc ceiling.* rFID 0.57 from frozen DINOv2-B tokens
  means our desc arm's 22.4 dB is limited by the small decoder + 6k-step
  recipe, **not** by the features — treat 22.4 dB as a lower bound on desc
  content, and cite RAE rather than reproducing Phase 1 from scratch.
- *Recipe donor.* Their LPIPS + scheduled-GAN loss and latent normalization
  are the upgrade path if R-line decoders need higher fidelity than L1+LPIPS
  delivers.
- *Warm start for R2's recon decoder* once training moves to bigger GPUs
  (swap the input projection, fine-tune the body).

## Read-out

PSNR/SSIM/LPIPS on held-out sequences vs. the SD-VAE anchors from the H-line
(H7b winner: 27.49 dB / 0.085 LPIPS @ 256px). If `mv` decodes well, the

**Conclusion: the matcher stages destroy appearance.** With the identical
decoder/data/recipe, RoMaV2's own *input* reconstructs ~10 dB better than
anything after mv_vit — so the ~12.5-13 dB floor is not a decoder-capacity
artifact. Grids: desc recons are faithful (colors, identity, texture); mv/dpt
recons keep coarse layout only and are dominated by repeating
positional-embedding textures. Notably `dpt` (128ch @ /4, least compressed)
is no better than `mv` — resolution isn't the bottleneck, information
content is. The premise of the project holds at the strongest possible
contrast; R2 (fine-tune with matching + recon loss, or from-scratch
training) has a large window to recover appearance, target: close the gap
toward the 22.4 dB desc ceiling without losing Mega-1500/ScanNet-1500
matching performance.

**mvdesc (2026-07-12): mv carries no *marginal* appearance either.**
(appendix with the full decoder spec at the end of this doc)
recon(desc+mv) = 22.50 dB ≈ recon(desc) = 22.43 dB, so the matcher adds
nothing reconstruction-useful beyond its own input. The ablations are
internally consistent: zeroing mv costs only ~1.1 dB (an upper bound on
mv's contribution, OOD effect included), while zeroing desc collapses to
12.99 dB — reproducing the mv-only arm (12.96 dB) almost exactly from
inside the joint decoder. Everything decodable lives in the frozen
descriptor. Consequence for R2: a desc skip into the recon decoder buys
fidelity "for free" but makes recon quality blind to what the matcher
retains — if R2 uses the skip architecture, the mv-only probe (no skip)
must stay as the measurement; if the goal is forcing appearance *into* the
matcher features, the recon loss must attach before the skip (mv or
earlier), not after it.

## Appendix — probe decoder (v3 RAEDecoder) in detail

`src/decoders.py` `RAEDecoder`, a faithful port of the RAE stage-1
decoder (arXiv:2510.11690, `GeneralDecoder` in github.com/bytetriper/RAE
= the HF ViT-MAE decoder). One instance per arm, identical everywhere
except the input embed.

**Dataflow** (input: raw fp16-cached feature grid `[B, C, H/s, W/s]` at
stride `s`; output: RGB `[B, 3, H, W]` in [0,1], clamped at eval, no
output activation):

1. **Input norm** — non-affine LayerNorm over channels (eps 1e-6). This
   replaces RAE's trick of cancelling the encoder's final-LN affine
   (paper C.1); RoMaV2 taps are raw maps, so the normalization happens
   here. For `mvdesc` it is applied *per source slice* (desc channels and
   mv channels separately), so the zeroed-source ablation stays
   interpretable (LN(0) = 0).
2. **Fold to /16 tokens** — features finer than /16 are folded
   `(16/s)²` spatial cells → one token (only `dpt` @ /4: 128ch × 4² =
   2048-dim token). Probe deviation: the paper's rule p_d = p_e would
   give 6400 tokens for dpt @ /4, infeasible on our GPUs. At 320px every
   arm therefore runs 20×20 = 400 tokens + 1 CLS.
3. **decoder_embed** — `Linear(C·(16/s)² → width)`. The only per-arm
   difference; for `mvdesc` it doubles as the learned desc/mv mixing
   projection.
4. **+ trainable [CLS] token, + fixed 2D sin-cos pos-embed** (MAE-style,
   zero row for CLS; rebuilt if the grid size changes).
5. **ViT body** — `depth` pre-LN blocks (MSA `heads` heads + MLP ×4
   GELU, LN eps 1e-12, HF ViT-MAE layer semantics).
6. **Head** — final LN → `Linear(width → 3·16²)` patch prediction → drop
   CLS → unpatchify to `[B, 3, H, W]`. `decoder_pred.weight` is the
   anchor for the VQGAN-style adaptive GAN weight.

Noise-augmented decoding (paper 4.3) is implemented on the normalized
latent (`--noise-tau`, RAE stage-1 default 0.8) but **off** in all probe
runs — it exists for diffusion-sampling robustness and would blur the
reconstructability read-out.

**Sizes** (paper Table 13; MLP ratio 4). Probe default **B**
(`--decoder-size`), body = everything except `decoder_embed`:

| size | width | heads | depth | body params |
|------|-------|-------|-------|-------------|
| S | 384 | 6 | 12 | 21.6M |
| **B (ours)** | 768 | 12 | 12 | 85.6M |
| L | 1024 | 16 | 24 | 303M |
| XL (paper default) | 1152 | 16 | 28 | 447M |

**Per-arm instances** (ViT-B, 320px → 400 tokens):

| arm | input | token dim after fold | embed params | total |
|-----|-------|----------------------|--------------|-------|
| `desc` | 2048ch @ /16 | 2048 | 1.57M | 87.2M |

**Capacity caveat (VRAM-forced).** The paper's default decoder is XL —
~5× our body parameters — and RAE reaches rFID 0.57 with it after ~20.5M
training samples; we run B for 48k samples because an XL at 320px with
the DINO-S/8 GAN discriminator does not fit an 11 GB 1080 Ti (no native
bf16, fp32 training; the B runs already sit at ~8.3 GiB). Decoder scale
(width/depth) plausibly has a large effect on *absolute* reconstruction
quality — v3-B desc (19.56 dB) landing below the tiny v1 ConvDecoder
(22.43 dB) shows the recipe, not the features, caps the numbers.
**Cross-arm comparisons remain valid** (identical decoder/recipe per
arm), but absolute PSNRs are lower bounds on feature content; if
absolute fidelity ever matters (R2 readouts, RAE-style generation),
rerun the winning arms at L/XL on bigger GPUs, or warm-start from the
released RAE decoders (see "Not used" section).

### Decoder-scale sweep (launched 2026-07-14)

Tests the caveat above directly: same recipe/steps on the `desc`
(ceiling control) and `b3` (R2 candidate) arms at sizes **S** (21.6M
body, ~0.25× B) and **L** (303M body, ~3.5× B), 3cat split. Two reads:
how much do *absolute* numbers move with capacity (is the probe
decoder-limited?), and does the desc↔b3 *gap* change (is the cross-arm
comparison scale-stable?).

Execution: `scripts/r1_scale_driver.sh`. The S runs fit one GPU each and
run in parallel. The L decoder does not fit an 11 GB 1080 Ti next to the
GAN discriminator, so it runs **model-parallel across both GPUs**:
`RAEDecoder.pipeline()` moves the second half of the blocks + final
LN/patch head to `cuda:1`, `forward()` shuttles activations between the
halves and returns on the input device, so the loss stack, LPIPS,
discriminator, EMA, and checkpointing are untouched (`--pipeline` in
`r1_recon_probe.py`; the adaptive GAN weight's gradient is taken on the
cuda:1 patch head and moved back). Results in
`results/r1_recon_probe/{desc,b3}_{S,L}/`.

| arm | S (21.6M) | B (85.6M) | L (303M) |
|-----|-----------|-----------|----------|
| `desc` | 19.50 / 0.359 | **19.56** / 0.341 | 19.16 / 0.377 |
| `b3` | 17.02 / 0.502 | **17.54** / 0.448 | 17.23 / 0.470 |

(PSNR dB / LPIPS, EMA; done 2026-07-14,
`results/r1_recon_probe/{desc,b3}_{S,L}/metrics.json`)

**Conclusion: decoder capacity is not what caps the probe.** Across a
14× parameter range every number moves within ±0.5 dB, with B best on
both arms and L slightly *worse* (larger model, same 48k-sample budget —
undertrained). So the absolute ceiling is set by the recipe's data/step
budget (paper: 20.5M samples), not model size, and buying bigger GPUs
would not change the probe's readings. The desc↔b3 gap is scale-stable
(2.0 dB @ B, 2.5 @ S, 1.9 @ L), so the cross-arm conclusions don't
depend on decoder capacity — mid-depth taps stay the R2 target.

Pipeline lessons (11 GB GPUs): the GAN-phase graph (decoder + LPIPS-VGG
+ DINO disc) dominates cuda:0, so the split puts only 1/6 of the blocks
there; and resume must load checkpoints with `map_location="cpu"` —
loading to cuda:0 pins a full extra model+EMA+optimizer copy (~4.8 GB at
L) for the whole run.
