# R1 — Reconstruction probe on frozen RoMaV2 features

New line (R-prefix), started 2026-07-08 after the H-line concluded. Context:
using a matcher like RoMa as a diffusion backbone (RAE-style, "Diffusion
Transformers with Representation Autoencoders") shows a tradeoff between
reconstructability and multi-view consistency. Long-term idea: fine-tune
RoMaV2 with its matching objective + an auxiliary reconstruction loss on the
DPT-head features. R1 measures the **frozen baseline endpoint** of that
tradeoff first: how reconstructable are stock RoMaV2 features, before any
fine-tuning?

## Setup

- RoMaV2 vendored in `third_party/RoMaV2` (inference-only upstream; weights
  auto-download to the torch hub cache). Frozen throughout R1.
- Features are pair-conditioned (mv_vit attends over both images). Two
  representations per pair (A, B), extracted via hooks (`src/romav2_utils.py`):
  - `dpt`: fused DPT-head map before `output_conv2`, 128ch @ H/4 — densest,
    ~512x less compressed than an SD-VAE latent, expected easy to decode.
  - `mv`: mv_vit tokens for view A, 1024ch @ H/16 — bottleneck-like, the
    RAE-comparable representation.
  - `desc` (control, added after first results): frozen DINOv3 descriptor of
    A (layers 11+17), 2048ch @ H/16 — the matcher's own input. Same decoder +
    data, so it separates "the matcher discarded appearance" from "our small
    decoder can't decode anything". Cached as `.desc.pt` sidecar files.
  - `mvdesc` (added 2026-07-12): `[desc ‖ mv]` channel concat, 3072ch @ H/16,
    through a learned 1x1 projection to 1024ch, then the same ConvDecoder
    body as `mv` (`ProjConvDecoder`). Assembled at load time from the cached
    desc+mv — no new precompute. Measures mv's *marginal* information beyond
    desc (recon(desc+mv) − recon(desc)), and is the R2 architecture
    candidate: a backbone skip into the recon decoder lets the matcher keep
    discarding appearance while the recon gradient shapes the encoder.
    Caveat: since desc alone is near its ceiling, the decoder may shortcut
    to desc and ignore mv — so this arm also reports eval-time source
    ablations (mv channels zeroed / desc channels zeroed) in metrics.json.
    Zeroed inputs are OOD for the decoder, so a drop only *upper-bounds* a
    source's contribution; `mv_zeroed ≈ full` is still conclusive (mv
    ignored). It does **not** replace the `mv`-only probe, which stays the
    clean trade-off measurement.
- Data: CO3D `EXTRACTED_CATEGORIES`, standard `split_seqs()` split. Pairs
  alternate near-/far-view conditioning. Features precomputed once (fp16) to
  `/visinf/projects_students/dlcv2025_groupZ/romav2_feats/r1_320/`.
- Decoder: `src/decoders.py` ConvDecoder (GroupNorm ResBlocks, x2 nearest
  upsampling), L1 + 0.1 LPIPS(alex), 6k steps Adam 2e-4 warmup+cosine,
  320px images in [0,1] (RoMaV2 convention, unlike the VAE's [-1,1]).

## Hardware notes (1080 Ti)

- amp disabled via cfg where possible; the DPT head's internal bf16 autocast
  is unconditional upstream but runs (emulated) on Pascal.
- Frozen full-model forward at 320px ("turbo"): ~2.6 GiB, ~1-3 s/pair.

## Run

`scripts/r1_driver.sh` in tmux: precompute cache, then one decoder per arm
(GPUs alternate; arms with a metrics.json are skipped, so re-running after
adding an arm only trains the new one). Results in
`results/r1_recon_probe/{dpt,mv,desc,mvdesc}/`.

## Not used: pretrained RAE decoders

Considered reusing the released RAE decoder checkpoints
(`nyu-visionx/RAE-collections`, `decoders/dinov2/wReg_{small,base,large}`,
ViT-XL bodies) instead of training our own. Rejected for R1: they expect
DINOv2-with-registers *final-layer* tokens — RoMaV2's descriptor is DINOv3
ViT-L layers 11+17 (2048ch) and `mv`/`dpt` are different feature spaces
entirely, so none of our arms match their input distribution; fine-tuning a
ViT-XL decoder at 320px is also impractical on the 1080 Tis. They remain
relevant as a Phase-1 reference ceiling (DINOv2 reconstruction quality on
ImageNet) and as a possible warm start once training moves to bigger GPUs.

## Read-out

PSNR/SSIM/LPIPS on held-out sequences vs. the SD-VAE anchors from the H-line
(H7b winner: 27.49 dB / 0.085 LPIPS @ 256px). If `mv` decodes well, the
tradeoff may already be mild at the representation that matters; if it
decodes poorly while `dpt` decodes trivially, the fine-tune (R2) should aim
its recon loss at the mv/bottleneck level.

## Results (2026-07-08, run.json in results/r1_recon_probe/*)

| features | PSNR | SSIM | LPIPS |
|----------|------|------|-------|
| `desc` (DINOv3 input, control) | **22.43** | 0.586 | **0.192** |
| `mv` (matcher bottleneck)      | 12.96 | 0.353 | 0.557 |
| `dpt` (head, densest)          | 12.49 | 0.300 | 0.536 |
| `mvdesc` (desc+mv, projection) | *running (launched 2026-07-12)* | | |

**Conclusion: the matcher stages destroy appearance.** With the identical
decoder/data/recipe, RoMaV2's own *input* reconstructs ~10 dB better than
anything after mv_vit — so the ~12.5-13 dB floor is not a decoder-capacity
artifact. Grids: desc recons are faithful (colors, identity, texture); mv/dpt
recons keep coarse layout only and are dominated by repeating
positional-embedding textures. Notably `dpt` (128ch @ /4, least compressed)
is no better than `mv` — resolution isn't the bottleneck, information
content is. The premise of the project holds at the strongest possible
contrast; R2 (fine-tune with matching + recon loss, or from-scratch
training) has a large window to recover appearance, target: close the gap
toward the 22.4 dB desc ceiling without losing Mega-1500/ScanNet-1500
matching performance.
